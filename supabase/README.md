## 1. Create the tables

1. Open <https://supabase.com/dashboard/project/uvlrbulfbwrkjknqcpqb/sql/new>
2. Open **`supabase/setup-all.sql`** from this repo, copy the whole file
3. Paste into the SQL editor and click **Run**
4. You should see "Success. No rows returned."

Use `setup-all.sql`, **not** `schema.sql`. `schema.sql` is only the original
base schema; on its own it leaves you ~21 migrations behind, missing `bookings`,
`app_settings`, `match_overrides` and more. `setup-all.sql` is schema plus every
migration in order.

The script is **idempotent** — every statement uses `IF NOT EXISTS` /
`ON CONFLICT`, so re-running it won't drop data or fail.

> `setup-all.sql` is generated by concatenating `schema.sql` with
> `migrations/*.sql` in filename order. Regenerate it that way after adding a
> migration; don't hand-edit it. An earlier hand-maintained copy had silently
> skipped migrations 0013–0018, which made it fail on a fresh database — 0020
> runs `alter table bookings` while 0015, which creates that table, was missing.

## 2. Grab the keys

In Supabase Studio → **Project Settings** → **API Keys**.

Supabase has moved to a new key format. The app needs two values:

| Env var | Which key | Notes |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL | `https://uvlrbulfbwrkjknqcpqb.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | **Secret** key (`sb_secret_…`) | Server only — bypasses RLS |

The publishable key (`sb_publishable_…`) is safe in a browser under RLS, but
nothing in `src/` reads it today: the app does its own bcrypt auth and every
query goes through server routes using the secret key.

Add them to `.env.local` (local, gitignored) and to Vercel → Settings →
Environment Variables (production):

```env
NEXT_PUBLIC_SUPABASE_URL=https://uvlrbulfbwrkjknqcpqb.supabase.co
SUPABASE_SERVICE_ROLE_KEY=sb_secret_...
```

Never commit the secret key — it gives full read/write on every table. If one
is ever pasted somewhere it shouldn't be (a chat, a log, a screenshot), rotate
it in the dashboard; revoking is instant and the old value stops working.

## 4. Row Level Security

RLS is **enabled** on every table. The only `anon`-readable thing right now is `custom_matches` (so the public matches API can show admin-added games even when the Odds API is rate-limited).

Everything else expects requests using the **service role key**, which bypasses RLS. The Next.js server-side routes (`/app/api/...`) are where that key gets used.

If you later want logged-in players to query their own data directly from the browser, add policies like:

```sql
create policy "users read self" on public.users
  for select to authenticated
  using (id = auth.uid());
```

That assumes you wire user records to Supabase's built-in `auth.users` table — separate decision. For now the app does its own bcrypt-based auth, so `auth.uid()` isn't populated, and everything flows through the server.
